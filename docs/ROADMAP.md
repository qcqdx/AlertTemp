## 0. Процесс: как этот проект работает

1. **Разработка ведётся вне стенда** (исполнитель не имеет доступа к
   10.10.0.50): юнит/интеграционные тесты на SQLite, живые прогоны с
   локальным Mosquitto и эмулятором (`devtools/controller_sim.py --seed`),
   миграции локально и в CI на настоящем TimescaleDB.
2. **Каждый этап завершается протоколом** для стенда: команды развёртывания
   (`git pull && docker compose up -d --build` — миграции применяются сами)
   и пронумерованные проверки с ожидаемыми результатами.
3. **Стенд прогоняет и присылает консолидированный отчёт** с находками по
   приоритетам (P-нумерация) и фактическими числами. Находки закрываются
   в первом же следующем коммите, каждая — с регрессионным тестом
   (`tests/test_stand_findings.py` и далее).
4. **Ядро детекции (rule engine) сейчас ЗАМОРОЖЕНО** — стенд собирает
   статистику на реальных циклах разморозки (недели). Не менять
   `app/rules/engine.py` без явного запроса стенда. Всё остальное
   (оповещения, UI, API, отчёты) — открыто для работы.
5. Ожидаемые события: **срез №2 от стенда** (~23.07.2026, компрессия первого
   Timescale-чанка: фактическая степень сжатия + тайминги на сжатых данных).
   После него — приёмка печатных форм.

## 1. Что уже сделано (карта кода)

| Подсистема | Где | Ключевые решения |
|---|---|---|
| Ingest MQTT | `app/ingest/` | батч-запись раз в 1 с; неизвестные топики → очередь обнаружения; топик = недоверенные данные; буфер возвращается при сбое БД |
| Хранение | `migrations/0001,0003` | hypertable + continuous aggregate `measurement_1m` (все графики/расчёты за периоды читают его, не сырьё); компрессия 7 дн; retention: raw 365 дн, агрегат 1100 дн |
| Rule engine | `app/rules/engine.py` | СОБЫТИЙНАЯ модель; state machine с гистерезисом и задержками; opened_at бэкдейтится к началу экскурсии; open_value/confirm_value; offline по таймауту = critical; состояние переживает рестарт |
| Оповещения | `app/notify/notifier.py` | изолированный старт (ошибка конфига не валит ingest!); SOCKS5 (socks5h→rdns); digest с окном группировки; напоминания с grace; эскалация кругами (tier); ack-кнопки + getUpdates-поллер; heartbeat-дайджест; reply-цепочки персистятся (`incident_message`) |
| Качество | `app/api/routes/quality.py` | MKT (ΔH/R=10000 K); время вне диапазона по минутным avg; `basis=current` (интерактив) / `historical` (отчёты); бюджет стабильности |
| Печатные формы | `app/api/routes/reports.py` + `ReportView.vue` | ЭСКИЗ (см. этап A): historical, эпохи профилей, слепые зоны, print-CSS |
| Auth | `app/api/auth.py`, `core/security.py` | argon2, серверные сессии, роли viewer/operator/admin |
| Аудит | `app/models/audit.py` | в одной транзакции с изменением; format_detail (без enum-repr); «было → стало» для reorder |
| UI | `frontend/` | Vue 3 + ECharts, поллинг (5–10 с), раздаётся FastAPI из `static/` |

Тесты: `backend/tests/` (114 на момент записи), CI (`.github/workflows/ci.yml`):
линт + тесты + миграции на TimescaleDB с проверкой hypertable/агрегата/политик.

## 2. Каталог паттернов проекта (ОБЯЗАТЕЛЕН к соблюдению)

Паттерны оплачены реальными инцидентами стенда. Нарушение любого из них —
регрессия, которую стенд поймает.

1. **Измерения — главный контур, всё остальное — вспомогательное.**
   Ошибка любой другой подсистемы не имеет права останавливать ingest
   (прецедент: опечатка в прокси стоила 93 с простоя и ~290 боевых
   измерений безвозвратно — QoS 0, буфера в железе нет).
2. **basis=historical для всего отчётного.** Интерактив может считать по
   текущему профилю (с подписью), печатное/журнальное — только по профилю,
   действовавшему на момент измерения. Версии профилей уже в БД
   (`threshold_profile.created_at` = начало эпохи).
3. **Слепые зоны — явно.** Отсутствие данных ≠ отсутствие нарушений;
   покрытие и интервалы разрывов показываются везде, где есть агрегаты.
4. **Групповые события схлопываются** (digest + окно группировки): целевой
   масштаб — 30 холодильников; отказ роутера = 90 offline; канал, который
   штормит, дежурные отключают.
5. **Персистентность через рестарт** для всего, что имеет жизненный цикл:
   состояние движка, escalated_tier, message_id reply-цепочек, счётчики
   напоминаний. In-memory допустим только как кэш поверх БД (и это
   документируется как известное поведение, если нет).
6. **Grace-период после старта** для повторяющихся уведомлений — рестарт
   поверх N старых объектов не должен давать N немедленных сообщений.
7. **Аудит в одной транзакции** с изменением; details через
   `format_detail()` (никаких Python-repr); «было → стало» для перестановок.
   Аудит неизменяем: бэкфиллы истории не делаются.
8. **Вся арифметика времени — в UTC** (`UTCDateTime` возвращает aware
   на обоих диалектах); таймзона — только на отображении
   (`display_timezone`). В URL-параметрах ISO-строки с `Z` (не `+00:00` —
   плюс в query превращается в пробел).
9. **Диалектная переносимость**: PostgreSQL/Timescale — прод, SQLite —
   тесты/dev. Дорогие пути (bucket, quality) имеют PG-ветку через
   `measurement_1m` и SQLite-fallback по сырым данным. Timescale-миграции —
   no-op без расширения.
10. **Кэш + инвалидация**: топик→датчик (ingest), инфо датчика (engine) —
    TTL 30 с + явная инвалидация из API-мутаций.
11. **env_file в compose**: любые `COLDWATCH_*` из `.env` доходят до
    приложения; НИКОГДА не возвращаться к явному списку переменных
    (класс бага P4).
12. **Прокси Telegram**: socks5h:// — рекомендуемая схема (CONNECT по IP
    может быть закрыт на прокси — живой прецедент); незнакомая схема —
    NotifyConfigError на старте, канал отключается, ingest живёт.
13. **Никаких удалений** сущностей с историей: только архивирование;
    архивный датчик освобождает топик и позицию.
14. **Тест на каждую находку стенда** — регрессия фиксируется до фикса
    поведения, файл `tests/test_stand_findings.py` (+ тематические).

## 3. Оставшиеся этапы

### Этап A — печатные формы: от эскиза до приёмки

Статус: **эскиз реализован** (`GET /api/v1/controllers/{id}/report`,
`ReportView.vue` c print-CSS). Стендовая приёмка — после среза №2.

Контракт (реализован): JSON-отчёт с шапкой (объект, период, кто и когда
сформировал, `basis=historical`, `metric_note`), по каждому датчику:
эпохи профилей (version, границы, `valid_from/valid_to`, пересечение с
периодом), итоги (samples, coverage, min/avg/max, MKT, out_above/below/total
по historical), слепые зоны (разрывы > 300 с, `GAP_THRESHOLD_S`),
инциденты периода. Лимит периода 92 дня.

Осталось до приёмки:
- [ ] прогон стенда по протоколу: сверка out_total_s с их независимым SQL
      (методика трёхсторонней сверки уже отработана в фазе 3.5), сверка
      слепых зон с известными окнами простоя, печать в PDF из браузера;
- [x] дефект цикла I (find_gaps на неупорядоченной выборке PostgreSQL)
      исправлен: `ORDER BY` в обеих ветках `_minute_buckets` + защитная
      сортировка внутри `find_gaps` + регрессионный тест с перемешанным
      входом (`test_stand_findings.py`); в `metric_note` добавлена фраза
      о минутном квантовании границ слепых зон;
- [x] отчёт по ОДНОМУ инциденту («отчёт по экскурсии»): период
      [opened_at − 1ч, closed_at + 1ч] вычисляет СЕРВЕР
      (`GET /api/v1/incidents/{id}/report`, незакрытый — по текущий
      момент); UI-роут `/incidents/:id/report` переиспользует ReportView,
      кнопка «Отчёт» — в каждой строке журнала инцидентов;
- [ ] критерии приёмки: числа historical воспроизводимы при повторном
      запросе; смена порогов после периода НЕ меняет отчёт; слепые зоны
      суммарно = (окно − minutes_with_data·60) ± граничные минуты;
      печать A4 без обрезания таблиц.

Решение против PDF-генерации на сервере (weasyprint и т.п.): печать из
браузера покрывает потребность проверяющих без тяжёлых зависимостей;
пересмотреть, только если стенд попросит автоматическую рассылку PDF.

### Этап B — полировка (из концепции, приоритет за стендом)

1. **Партии/загрузки** (концепция §6.3): персонал отмечает дату помещения
   партии в холодильник; бюджет стабильности и MKT считаются от даты
   загрузки, а не от скользящего окна. Модель: `batch(controller_id,
   label, loaded_at, unloaded_at?)`; quality/report принимают
   `since=batch:<id>`. Миграция + CRUD (admin) + выбор в UI.
   Осознанно НЕ включено в расширенный проход цикла I (п. 6 был
   опциональным) — идёт следующим проходом отдельным срезом.
2. **Экспорт CSV/Excel** журнала инцидентов и отчёта — СДЕЛАНО (цикл I):
   `GET /api/v1/incidents/export.csv` (фильтры те же, что у списка) и
   `GET /api/v1/controllers/{id}/report.csv` (сводка по датчикам).
   Формат: UTF-8 с BOM, разделитель `;` — Excel открывает без настройки.
   Кнопки «⬇ CSV» в журнале инцидентов и на форме отчёта.
3. **WebSocket вместо поллинга** — только при жалобах на нагрузку/задержку;
   шина событий уже есть (`core/bus.py` — подписка возвращает Queue),
   endpoint `/api/v1/ws` с раздачей MeasurementEvent/IncidentEvent.
4. **i18n-каркас** — строки UI в словарь; актуально только при втором языке.
5. **Персистентность consecutive_failures** — если эксплуатация покажет,
   что рестарты маскируют деградацию канала (пока принято как известное
   поведение).

## 4. Инварианты аппаратной части (не менять — это железо)

- MQTT, payload — голый float (°C), топик = id датчика (`temp/<uid DS18B20>`).
- Контроллер себя НЕ обозначает; контроллер в системе — логическая группа,
  собираемая администратором из обнаруженных топиков.
- Темп боевой прошивки: пачка из 3 PUBLISH ~каждую секунду (~3.15 msg/s
  с контроллера, ~272 тыс. строк/сутки). Прошивка необслуживаемая.
- Heartbeat отсутствует: offline только по таймауту тишины; «датчик,
  контроллер или сеть» неразличимы по данным.
- QoS 0, буфера нет: недоставленное потеряно навсегда; простой ingest =
  безвозвратная слепая зона.

## 5. Как сдавать этап (шаблон)

1. Код + миграция (нумерация `00NN_*.py`, откат обязателен) + тесты
   (регрессия на каждый пункт протокола, который можно проверить локально).
2. `ruff check` чист; `pytest` зелёный; `alembic upgrade head` на чистой
   SQLite проходит всю цепочку; frontend собирается.
3. Коммит: описание на английском, со ссылками на находки стенда, которые
   закрывает; пуш в рабочую ветку.
4. Финальное сообщение: что сделано → **протокол проверки для стенда**
   (команды + пронумерованные проверки с ожидаемыми числами) → что дальше.
5. Не начинать следующий этап до отчёта стенда, если этап помечен
   «приёмка стендом»; исключение — параллельный фронт, не трогающий
   проверяемое.
